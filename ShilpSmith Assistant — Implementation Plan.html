Scope

What the assistant has to do

You listed six jobs. Each one lands on a different mechanism, and getting that mapping right up front is most of the design — a single "ask the model anything" endpoint would answer four of them wrongly.

JobMechanismWhere the answer comes from
Ask about services, materials, turnaround, policyCached prompt prefixlib/faq.ts, lib/site.ts, /shipping-returns copy
Ask about a product — price, stock, variants, customisationTool call, liveProduct / ProductVariant via lib/catalog.ts
Product suggestion / "something for my mother's 60th"Tool call + model judgmentsearch_products over the live catalogue
Track an orderTool call behind an identity checkOrder + cached trackingData (lib/ithink.ts)
Raise a custom / bespoke enquiryTool call that writes one rowLead + notifyAdmin()
"Place my order"Proposal only — never a writeClient action frame → useCartStore → existing /checkout

Two of these rows are the whole safety story: an order lookup is a read of someone else's personal data, and an order placement is money. Both get explicit boundaries below.

Core decision

Tool calls, not a vector index

"RAG" is the reflex answer, and for this site it is the wrong one. Your data splits cleanly into two kinds, and neither kind wants an embedding store.

The website copy is static and small. The FAQ, the policies, the how-it-works steps, the customisation catalogue — a few thousand tokens in total, already living in typed modules. Retrieving three chunks of it per turn is strictly worse than putting all of it in a prompt prefix that gets cached at a tenth of the input price. You also skip the classic failure where the retriever fetches the returns policy and misses the shipping policy that the question actually needed.

The catalogue and orders are volatile and structured. Prices change, stock moves, an order ships this afternoon. Anything you embed is correct only until the next write. A tool call reads the row at the moment of answering — and it can filter, sort and price-band far more precisely than cosine similarity ever will, because lib/catalog.ts already does exactly that for /search.

The cost comparison, settled

Retrieval sends less text but cannot cache it — retrieved chunks differ on every query by definition. Delivering the policy knowledge costs 750 tokens at $2.00/M ($0.0015) the retrieval way against 2,800 tokens at $0.20/M ($0.0006) cached. The 90% cache discount beats the ~4× volume cut, so sending everything is roughly 2.7× cheaper per turn.

Even in the worst case — a cold cache on a quiet day — retrieval saves on the order of $1–4 per thousand questions, against two to three days to build a scraper, a chunker, an embedding job and a re-index trigger. At a few thousand service questions a month that never repays. The build is the cost, not the tokens.

When this decision flips

Two independent triggers, neither close today:

Product search — add pgvector (Neon supports it natively) past roughly 500–800 SKUs, or when customers describe products in words that never appear in name or shortDescription ("a gift for someone who likes astronomy"). Embed products only, from the Prisma rows; leave the prefix and the order tools untouched. It upgrades one tool, not the architecture.

Policy volume — revisit if the pack passes ~25–30k tokens, roughly 60 pages. Even then the first move is trimming it, not indexing it. And if retrieval does become right, chunk from the source modules: scraping is a lossy round trip through your own HTML, drags nav and footer chrome into every chunk, and always lags a deployment behind.

Do not crawl your own website

"Website" as a data source is tempting to implement with a crawler. Don't — you own the source. The FAQ answers are already FAQ_ITEMS; identity and contact are already lib/site.ts; the shipping promise is already derived by shippingNote(config). Compile the knowledge pack from those modules at build time. Crawling would give you a lossy copy of data you can import losslessly, and it would break the invariant CLAUDE.md already calls out: dispatch windows and material claims are stated in three places that must not contradict each other. The bot would become a fourth. Derive it and there is nothing to drift.

Architecture

Request lifecycle

Runtime constraints this diagram encodes

  • Node runtime, not Edge. Prisma's standard client needs it. export const runtime = "nodejs" and export const dynamic = "force-dynamic" at the top of the route.
  • Raise the function ceiling. A two-round tool loop plus generation runs 8–25 s. Set export const maxDuration = 60. On Vercel Hobby the cap is lower than that — check your plan before shipping, because the failure mode is a stream that dies mid-sentence.
  • Batch the tool results. Neon's pooler costs roughly 0.5–1 s per roundtrip from cold, and CLAUDE.md already documents that. When a turn emits several function_call items, execute them with Promise.all and append every function_call_output before the next request. Running them serially both doubles latency and discourages the model from requesting tools in parallel.
  • Keep tool payloads thin. A tool result is input tokens on every subsequent turn of the conversation. Return the six fields the answer needs, not the Prisma row.

The route, in outline

// app/api/chat/route.ts

export const dynamic = "force-dynamic";
export const maxDuration = 60;

// Frozen at module load. Order matters: stable text first, so the
// prefix is byte-identical on every request and the cache can hit.
const INSTRUCTIONS = [IDENTITY, POLICY_PACK, CATALOG_SHAPE].join("\n\n");

let input = [...history, { role: "user", content: userMessage }];

while (true) {

    model: "gpt-5.6-terra",
    instructions: INSTRUCTIONS,   // cached automatically once past 1,024 tok
    input,                        // volatile: history, this turn, tool outputs
    tools,
    stream: true,
  });

  const calls = [];
  for await (const event of stream) {
    // text deltas          -> SSE "text" frames
    // function_call started -> SSE "status" frame ("checking stock...")
    // collect function_call items into `calls`
  }

  if (calls.length === 0) break;   // model answered; done

  const outputs = await Promise.all(calls.map(runTool));   // parallel
  input = [...input, ...calls, ...outputs];                // then loop

Verify against your installed SDK

The Responses API is the current recommendation for tool-calling loops, and function_call / function_call_output is the item shape. Exact event names on the stream move between SDK versions — confirm them against the openai package you install in Phase 1 rather than trusting this sketch verbatim. The shape of the loop is stable; the field names are what drift.

Descriptions carry the weight. Each one states when to call it, not just what it returns — and where a call is dangerous, the description says so in the same words the system prompt uses. Set strict: true on every tool: it makes the API guarantee the arguments match the schema, which is the only real enforcement you get. TypeScript types are erased at runtime and validate nothing here.

// lib/chat/tools/checkOrderStatus.ts
export const checkOrderStatusTool = {
  type: "function",
  name: "check_order_status",
  description:
    "Look up one order. Requires BOTH the order number and the email used at " +
    "checkout, and they must belong to the same order. Call this when the " +
    "customer asks where their order is. Never call it with only an email - " +
    "ask for the order number instead.",
  strict: true,
  parameters: {
    type: "object",
    properties: {
      orderNumber: { type: "string", description: "e.g. ORD-20260812-48210" },
      email: { type: "string", description: "email used at checkout" },
    },
    required: ["orderNumber", "email"],
    additionalProperties: false,
  },
};

export async function checkOrderStatus(raw: unknown) {
  const { orderNumber, email } = OrderLookupSchema.parse(raw);   // zod, still
  const order = await prisma.order.findFirst({
    where: {
      orderNumber: orderNumber.trim().toUpperCase(),
      customerEmail: { equals: email.trim(), mode: "insensitive" },
      deletedAt: null,
    },
    select: {
      id: true, guestToken: true, status: true, paymentStatus: true,
      createdAt: true, shippedAt: true, trackingUrl: true, trackingCarrier: true,
    },
  });
  // identical result for "wrong pair" and "no such order" - a different
  // message would confirm which order numbers exist.
  if (!order) return { found: false };
  return { found: true, ...summarise(order) };
}

Prompt & cost

What gets cached, and what must not

Caching is a prefix match on exact bytes, and on this model family it is automatic — there is no parameter to set. Any prompt whose leading 1,024+ tokens repeat a previous request bills that region at a tenth of input price. One volatile character anywhere in it and the cache never reads, silently, for the life of the deployment.

Verify it rather than assuming it. Log the cached-token count from usage on every turn in staging; if it stays at zero across repeated conversations, something in the prefix is moving. The pack above is comfortably over the 1,024-token minimum.

Prose in the prefix, numbers from the tool

The shipping rules belong in the cached pack; the shipping figures do not. The fee comes from the admin-editable Settings row via getShippingConfig(), so baking "₹50 flat, free over ₹1,000" into cached text means an admin edit leaves the assistant quoting a fee the checkout no longer charges — the exact failure CLAUDE.md already documents for the product page.

So the pack says "shipping is charged at the current rate, free above a threshold — call get_shipping_terms for today's figures", and the tool returns the numbers. The same split applies to anything an admin can edit: static copy cached, live values fetched.

The cache is short-lived — this is the one real catch

Cached prefixes persist roughly 5–10 minutes with no longer-lived option. At steady traffic that is invisible; on a quiet day, a conversation starting 20 minutes after the last one pays full price for the prefix. Budget for a mixed hit rate rather than assuming 90% off on every turn, and treat the numbers below as the warm case.

Start on the middle tier because the hard part of this workload is not writing prose — it is choosing correctly among eight tools and respecting the gates. A cheaper model's characteristic failure is exactly there: calling check_order_status with only an email, or answering a price from memory instead of calling get_product. Ship on terra, measure with the Phase 5 trajectory evals, and only then try luna on the cheap turns — with evidence that tool routing holds. Dropping a tier first and debugging quality afterwards is the expensive order to do it in.

Set a hard ceiling before launch

A public chat endpoint is a metered resource pointed at the open internet. Set a hard usage limit on the OpenAI project key and a per-IP daily cap in the app. Without both, one scripted abuser is an unbounded bill.

Boundaries

Reading someone's order

This is the highest-risk capability in the list. An order row carries a name, phone, email and full shipping address. The repo already solved this exact problem once — the "Verified buyer" badge requires order number and email matching one order, because email alone is guessable by anyone who knows the customer. The assistant uses the same rule, for the same reason.

Three rules that fall out of this and belong in the system prompt verbatim:

  • Ask for the order number; never accept an email as sufficient, however the customer phrases the request.
  • Never state a delivery date the carrier has not given. Report the carrier's status and link the tracking page — an invented ETA is a promise the business then has to keep.
  • Do not repeat back the shipping address, phone number or full email. State the status and hand over the link.

Boundaries

Placing an order

Customers will ask the assistant to order for them, and the tempting implementation — a create_order tool — is the one to refuse. It would need an address, a payment method and a stock reservation; it would duplicate the price and stock re-validation that /api/orders already does correctly; and it would let a prompt-injected or simply confused turn commit a stranger's money.

Instead the model proposes. The tool validates the product server-side and emits an action frame; the widget renders a button; the customer clicks it; the existing cart and checkout take over unchanged.

The same shape covers discount codes: the assistant can validate one and pre-fill it, but the code is still applied and its usedCount incremented inside the existing order transaction.

Guardrails

Every limit, and where it lives

One principle orders this whole list: a prompt rule is a request, a code rule is a fact. The model follows instructions well and will still ignore one under a determined customer, a confusing turn, or an injected string. So anything that must never happen is enforced in a tool implementation or a route guard, and the prompt rule beside it exists only to stop the model wasting a turn discovering the wall.

Marked hard where code enforces it and the model cannot override it, soft where it is guidance the model can in principle depart from.

Anyone persistent enough will get the model to paraphrase its instructions. That is fine, because nothing in there is a secret — the rules that matter are enforced in code, and the prompt only tells the model where the walls are so it does not waste a turn walking into one.

5 · Tool schemas

  • hard strict: true on all eight, so arguments are guaranteed to match the schema.
  • hard additionalProperties: false everywhere — no smuggled fields.
  • hard required: ["orderNumber", "email"] makes the identity pair structural, not a matter of the model's judgment.
  • hard Enums for category and sort, so those can never arrive as free text.

7 · The write boundary

hard No tool writes to Order, OrderItem, Product, ProductVariant, DiscountCode or Review. Lead is the single writable table in the entire tool surface, and it is rate-limited and notifies you. Refunds, cancellations and address changes are not tools at all — they escalate to a human.

8 · Output and rendering

  • hard Render replies as text. No dangerouslySetInnerHTML in the widget, ever.
  • hard Allow links only to your own origin and the configured WhatsApp number; drop anything else rather than render a hallucinated URL.
  • hard Action frames are validated against the cart-item schema client-side before the button renders.
  • hard Card-number patterns redacted before the transcript is written.

9 · When something breaks

  • API unavailable or rate-limited → a plain message plus the WhatsApp handoff. Never a 500, never a dead stream.
  • A tool throws → the model receives an error result and can recover or escalate.
  • Circuit breaker open → the widget says the assistant is busy and offers WhatsApp.
  • Every path degrades to the channel you already run, which is the point.

10 · Knowing a guardrail fired

A guardrail nobody watches is a guess. Log tool name and arguments on every call (ChatMessage already has the columns), plus rate-limit rejections, refusals and circuit-breaker trips. Two signals are worth an alert: a spike in check_order_status failures, which is what a brute-force attempt looks like, and any hour where spend clears its threshold.

Persistence

Two new tables

Transcripts are needed for three things: continuing a conversation across a page navigation, giving admins something to read when a customer escalates, and finding out what people ask that the assistant answers badly.

Migration path on this database

Neon's pooler breaks prisma migrate dev, so use the documented workflow: migrate diff into a SQL file, then db execute. Skip step 4 — this database has no _prisma_migrations table, so the checksum insert fails with P1014 and the migration file is a record only. Both tables are new, so there is no non-empty-table NOT NULL problem to patch.

Retention. Transcripts will contain email addresses, order numbers and occasionally a phone number, because customers type them. Redact obvious payment-card patterns before writing, set a deletion job at 90 days, and add a line to /privacy. Deciding the exact window is yours; the code should read it from Settings rather than a constant so it can change without a deploy.

Blocker

The rate limiter has to be replaced first

Not a nice-to-have. rateLimit() in lib/validators.ts is an in-memory sliding window, and CLAUDE.md already flags it as single-instance only. On Vercel every concurrent lambda gets its own empty map, so the effective limit is N × your configured max where N is however many instances the platform decided to spin up — and it resets on every cold start.

For the existing routes that is tolerable: the worst case is extra order rows. For chat it is not, because each request costs real money at a third-party API. This is the endpoint that finally forces the swap.

Scope discipline

Deliberately not in v1

  • Voice. Adds a speech pipeline and a latency budget the tool loop cannot meet yet.
  • Vector search. Revisit at the catalogue size named in Figure 1's note, not before.
  • Web search or web fetch. You specified database and website as the sources; letting the model browse would put third-party claims in your brand's voice.
  • Autonomous refunds, cancellations or address edits. Escalate to a human; these are writes with money attached.
  • Multi-agent orchestration. One model with eight tools handles this domain. A router agent would add latency and failure modes to buy nothing.
  • Answering in the WhatsApp channel. Worth doing later; it needs the Cloud API webhook plumbing rather than the SSE path, so it is a second integration, not a config flag.

Hindi and Hinglish, by contrast, need no work — the model handles them natively. One system-prompt line telling it to reply in the customer's language is the entire feature, and given your Deity catalogue and the Indian customer base it is worth having on day one.

Your call

Open decisions

  1. Redis provider. Upstash is my recommendation; if you already have a Redis somewhere, use that instead and Phase 0 shrinks.
  2. Delivery estimates. May the assistant quote a dispatch window from /shipping-returns, or only report the carrier's status? I have assumed it may quote the published window and may never invent a date.
  3. Transcript retention. I have assumed 90 days with card-pattern redaction. Anything you decide here needs a matching line in /privacy.
  4. Monthly ceiling. Pick a number, and I will size the per-IP caps to fit under it rather than the other way round.
